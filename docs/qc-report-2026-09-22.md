## 4. Findings & Recommendations

### 4.1 Build caching incident (follow-up required)

During development, `npm run build` produced a stale `dist/` (the new `Cheat` button was absent from the built JS even though the source was updated and typecheck passed). The issue was only resolved after `rm -rf dist && npm run build`.

**Recommendation:** Add a clean build step in CI/package scripts, e.g. `rm -rf dist && vite build`, or investigate whether a Vite/Babel cache in `node_modules/.vite` caused the stale output.

### 4.2 Native HTML5 drag only (desktop-friendly, touch gap)

The plan proposed a custom pointer-based ghost drag. What shipped uses native HTML5 drag-and-drop because it is simpler and produces the requested ghost image automatically. This works well with a mouse but is less reliable on touch devices.

**Recommendation:** If mobile cheat usage is desired, replace HTML5 DnD with custom `pointerdown/move/up` handlers in a future iteration.

### 4.3 Button pulse animation broke e2e stability

The first implementation pulsed the recommended button with `transform: scale(...)`. Playwright refused to click it because the element was "not stable". It was fixed by switching the pulse to `opacity` only.

**Recommendation:** Avoid `transform` animations on elements that tests (or users) need to click.

### 4.4 `legalMoveHints` relies on reference equality

The helper decides whether a move is legal by checking if an internal apply function returns the exact same state object (`applyXxx(state, ...) !== state`). This is true today but brittle: a future refactor that always returns a new object would make every candidate appear legal.

**Recommendation:** Add explicit legality predicates or at least a regression test that asserts an illegal move returns no hint.

### 4.5 Strict-mode e2e locator

`expect(arrows.or(sources)).toBeVisible()` failed because multiple matching elements exist. The fix (`first()`) is acceptable but a count assertion (`toHaveCountGreaterThan(0)`) would be more robust.

### 4.6 Heuristic is simple, not strategic

`recommendedPhaseAction` recommends Commit in Inspect only if a foundation move is currently visible. It does not compute expected value or look ahead.

**Recommendation:** Document this limitation in the UI (e.g. "Coach suggests moves, not perfect strategy") and consider a future ADR if a deeper solver is wanted.

### 4.7 Arrow marker visibility

In `media/05-cheat-mode.png` the arrowheads are small against the dark felt. Consider a larger marker or a drop-shadow for better contrast.

### 4.8 Repetition in `Table.tsx`

Drag handlers and source/target closures are repeated for foundations, tableaus, stock, and talon. A small helper mapping pile type to index would reduce duplication. Not blocking.
